# Agent 目录自然阅读次序模式

> **来源**：2026-06-23 会话中用户要求展示"被@到一个目录时的真实理解过程"，本文档是该过程的结构化沉淀。
> **性质**：认知模式文档，不是操作手册。供后续 Agent 在遇到同类场景时参考其思维路径，而非替代具体任务的 SOP。


## 1. 触发条件

以下任一情形出现时，Agent 会本能地启动本文档描述的阅读流程：

- 用户通过 `@路径` 或文本引用指向一个目录
- 用户说"看看这个目录"、"了解一下这个目录"
- 用户要求基于某个目录做决策（如"部署它"、"修改它"），但 Agent 尚未建立对该目录的认知
- Agent 在任务执行中需要首次进入一个陌生子目录（如 `references/tasks/<new-task>/`）

> **核心原则**：先建立全局认知，再按需下沉。禁止在尚未理解"这是什么"之前就动手执行文件操作。


## 2. 五层阅读次序

Agent 的自然认知路径分为五个层次，从外向内、从粗到细。每一层都会产生一个"判断"，决定下一层是否继续、或是否可以提前终止。


### Layer 1：目录内容扫描（本能反应）

**行为**：`read` 目标目录，获取文件名和子目录列表。

**关注信号**（按优先级排序）：

| 信号 | 含义 | 典型示例 |
|------|------|---------|
| `README.md` / `index.md` | 有自说明要求，是结构化目录 | 几乎所有工程目录 |
| `ENTRY.json` / `manifest.json` / `task-config.json` | 有机器可读真源，是任务/工具单元 | `deploy-git-isolated/ENTRY.json` |
| `DESIGN.md` / `GOAL.md` / `SOP.md` | 有完整生命周期文档，非临时脚本 | 工程化任务目录 |
| `schema/` / `scripts/` / `src/` | 有骨架+实现，可复用 | 工具链、任务包 |
| `gotchas/` / `changelog/` / `archive/` | 有演进历史，长期维护 | 成熟项目 |
| 零散脚本（`.ps1`、`.py` 无组织） | 可能是临时产物，需谨慎 | `debug/` 下的某些子目录 |

**输出判断**：

- 有 README + 结构化子目录 → 进入 Layer 2
- 只有零散文件，无 README → 快速扫一眼文件名后，视情况向上追溯父目录
- 完全空目录 → 报告用户，询问意图


### Layer 2：入口文档阅读（找"人话说明"）

**行为**：读取 `README.md`（或 `index.md`、`SKILL.md`）。

**关注重点**：

1. **frontmatter**：title / description / date → 判断文档时效性和主题域
2. **状态声明**："状态：ready"、"版本：v0.x" → 判断该目录当前是否可用
3. **快速决策表**：如果 README 中有表格化的"用户意图 → Agent 判断 → 执行路径"，直接记录
4. **文件导航表**：README 中是否已列出"各文件职责"，作为后续精准阅读的索引

**输出判断**：

- README 明确告诉我"这是 Agent 操作手册" → 按手册内的场景路径执行
- README 是面向人类的项目介绍 → 继续读机器真源（Layer 3）
- README 缺失或过时 → 自行扫描目录结构建立认知，并标记风险


### Layer 3：机器真源阅读（找"结构化契约"）

**行为**：读取 `ENTRY.json`、`manifest.json`、`*-config.json` 等机器可读文件。

**关注重点**：

1. **版本历史**：`meta.version_history` → 判断项目活跃度和演进脉络
2. **契约定义**：步骤（steps）、场景（scenarios）、输入/输出 schema → 理解"什么条件下做什么"
3. **脚本清单**：`active_scripts` / `tools` → 建立可用工具的全局索引
4. **依赖关系**：哪些脚本依赖哪些配置 → 避免执行时缺省

**输出判断**：

- 机器真源完整 → 建立"脚本→场景→触发条件"的映射表
- 机器真源缺失 → 退回到目录扫描，人工建立文件职责映射
- 机器真源与 README 矛盾 → 以机器真源为准（JSON 是执行依据），但标记文档不一致风险


### Layer 4：父目录追溯（找"部门坐标"）

**行为**：`read` 父目录及祖父目录，理解目标目录在项目中的"部门归属"。

**关注重点**：

1. **同级目录有哪些**：`references/tasks/` 下只有 `deploy-git-isolated/` → 说明它是当前唯一任务
2. **父目录 README**：`references/tasks/README.md` → 理解"这个部门是干什么的"
3. **祖父目录结构**：`references/` 下有 `runtime/`、`tasks/`、`env-migrations/` → 判断该目录属于"参考/规范/真源"层，而非应用代码层

**输出判断**：

- 明确目录的"组织坐标"（如：这是项目级基础设施，不是业务代码）
- 明确目录的"同级生态"（如：tasks 下还有其他任务吗？）
- 若目录归属与任务性质冲突 → 标记架构异常（如：业务代码出现在 `references/` 下）


### Layer 5：按需深入（精准阅读）

**行为**：根据前四层建立的认知，结合用户具体意图，精准读取特定文件。

**不是通读，而是按需下沉**：

| 用户意图 | 精准阅读目标 |
|---------|-------------|
| "部署它" | `README.md` 场景路径 + `SOP.md` Step 契约 |
| "它的设计思路是什么" | `DESIGN.md` + `GOAL.md` |
| "有哪些工具可用" | `TASK-TOOLS-INDEX.md` / `ENTRY.json` 的 `active_scripts` |
| "执行命令速查" | `scripts/EXEC-CHEATSHEET.md` |
| "它的规范基线是什么" | `task-canonical-baseline.md` |
| "这个目录安全吗" | `github-safety-check.ps1` 或 `.gitignore` 内容 |

**输出判断**：

- 按需读取后，建立"意图→文件→执行"的最短路径
- 若用户意图模糊 → 返回 Layer 2 的快速决策表，请用户确认


## 3. 从"理解"到"执行"的衔接模型

五层阅读完成后，Agent 的脑海中应形成以下三张表，才能开始执行：

### 表 A：目录认知卡片

```
目录名: deploy-git-isolated
组织坐标: references/tasks/ 下的标准化任务单元
性质: 工程化任务包（有生命周期文档 + 机器真源 + 插件架构）
状态: 核心功能 ready（v0.16.0）
主要能力: 隔离 Git 部署、GitHub 连接、安全检查、Issue 同步
```

### 表 B：意图映射表

| 用户说 | 文件入口 | 执行脚本 |
|--------|---------|---------|
| "部署隔离 Git" | README 场景 A | Step 1→8 |
| "连 GitHub" | README 场景 B | Step 6→8 |
| "检查哪些文件会传上去" | README 场景 C | `github-safety-check.ps1` |
| "git status" | README 场景 D/E | `git-isolated.ps1 status` |

### 表 C：风险清单

- `.env` 中是否已配置必要变量？
- 是否有运行中进程会冲突？
- 是否有未声明的敏感文件可能泄漏？

> **铁律**：三张表未建立完整之前，不开始执行任何会改变磁盘状态的命令。


## 4. 反模式（Agent 不应怎么做）

以下行为违背本文档描述的自然认知路径，属于"未理解先动手"：

| 反模式 | 危害 | 正确做法 |
|--------|------|---------|
| 直接 `glob` 找 `.ps1` 就执行 | 忽略前置条件和场景匹配，可能执行错误脚本 | 先读 README 和 ENTRY.json，确认脚本归属的场景 |
| 跳过 README，直接读代码 | 失去"人话说明"层的上下文，理解碎片化 | 先读 README，建立全局认知 |
| 只读当前目录，不向上追溯 | 无法理解目录在项目中的坐标和约束 | 读父目录 README，理解部门边界 |
| 通读所有文件再回复 | 浪费 token，信息过载 | 按 Layer 5"按需深入"，只读与意图相关的文件 |
| 凭记忆引用文件内容 | 上下文可能已过期 | 每次进入目录先读最新文件，不依赖记忆 |


## 5. 实例走查：以 `deploy-git-isolated` 为例

以下还原 2026-06-23 会话中 Agent 的真实阅读路径：

**Step 1**：`read deploy-git-isolated/` → 看到 17 个条目，判断为"结构化任务包"

**Step 2**：`read README.md` → 确认是"隔离 Git 部署任务"，有 6 个场景决策表

**Step 3**：`read ENTRY.json` → 确认版本 v0.16.0，有 8 个 Step 的 Ralph Loop 契约，5 个场景触发器

**Step 4**：`read references/tasks/` + `read references/tasks/README.md` → 确认是 tasks 部门下唯一的活跃任务

**Step 5**：`read references/` → 确认属于"参考/规范/真源"层

**结果**：建立完整认知后，向用户输出五层理解的结构化总结。

> **关键细节**：Agent 不是按"从上往下"读所有文件，而是按"信号驱动"——先扫目录获取信号，再按信号优先级选择下一步读取目标。这与人眼浏览网页的行为一致：先看标题和导航，再决定是否点进详情页。


## 6. 适用范围与边界

**适用**：

- 项目内任何包含 README + 结构化子目录的工程目录
- `references/tasks/`、`apps/`、`docs/projects/` 下的任务/项目单元
- 用户通过 `@路径` 主动指向的陌生目录

**不适用**：

- 单文件场景（如用户直接给出一个 `.py` 文件路径）
- 已知目录（Agent 已在当前 session 中读过，认知仍有效）
- 纯数据目录（如 `venv/tmp/`、`out/reports/`），这些目录通常无 README，直接按需读取目标文件即可


## 7. 演进建议

本文档记录的是一种"本能认知路径"，不是强制 SOP。后续可在以下方向演进：

1. **与 task-template 集成**：将五层阅读模式写入 `schema/task-template/` 的骨架文档，作为新建 task 时 Agent 的默认认知模板
2. **与 ENTRY.json schema 对齐**：在 `ENTRY.json` 中增加 `agent_reading_order` 字段，让机器真源也承载认知路径信息
3. **异常模式沉淀**：当 Agent 在某目录的阅读过程中遇到"信号与预期不符"的情况（如 README 存在但为空、ENTRY.json 与 README 严重冲突），应将异常记录到 `gotchas/` 下
