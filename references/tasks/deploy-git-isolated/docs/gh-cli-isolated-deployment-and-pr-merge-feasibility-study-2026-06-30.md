# gh CLI 隔离部署与 PR Merge 自动闭环可行性深度研究

## 执行摘要

| 维度 | 结论 |
|------|------|
| **gh CLI 隔离部署** | 完全可行。官方提供 Windows amd64 ZIP，解压即用，支持 `GH_CONFIG_DIR` 环境变量实现配置隔离 |
| **PR Merge 自动化** | 技术上可行，但需澄清认知偏差。`gh pr merge` 本质是远程 GitHub API 调用的命令行封装，不是本地 git 操作 |
| **与现有 workflow 集成** | 可在 `workflow-deploy-full.py` 后新增 Step 10（PR Create）和 Step 11（PR Merge），或作为独立 workflow |
| **整体价值评估** | 中等。单人仓库可直接 push 到 main，无需 PR；在分支保护 + Code Review 场景下价值显著 |


## 一、gh CLI 技术画像

### 1.1 发布渠道与版本

| 项目 | 详情 |
|------|------|
| **官方仓库** | `github.com/cli/cli` |
| **最新版本** | `v2.95.0`（2026-06-17 发布） |
| **Windows 资产** | `gh_2.95.0_windows_amd64.zip`（约 9.5 MB） |
| **下载直链** | `https://github.com/cli/cli/releases/download/v2.95.0/gh_2.95.0_windows_amd64.zip` |
| **内部结构** | 解压后 `bin/gh.exe` + `share/` 文档，`bin/` 目录可直接加入 PATH |

### 1.2 与 git.exe 的关系（关键澄清）

| 操作 | 是否依赖本地 git | 说明 |
|------|-----------------|------|
| `gh pr create` | 部分依赖 | 需要读取本地分支和 commit 信息 |
| `gh pr merge` | **不依赖** | 纯 GitHub API 调用，不执行本地 git 命令 |
| `gh pr checkout` | 强依赖 | 内部调用 `git fetch` + `git checkout` |
| `gh auth setup-git` | 强依赖 | 配置 git 的 credential helper |

> **核心认知**：`gh pr merge` 只是用命令行替代了在 GitHub Web 页面上点击 "Merge pull request" 按钮。代码合并在**远程服务器**上完成，本地磁盘不会发生任何变更。


## 二、隔离部署可行性分析

### 2.1 部署路径规划

```
d:/download/gh_2.95.0_windows_amd64.zip  <- 下载到 toolchainroot
    解压
devroot/venv/gh/
├── bin/
│   └── gh.exe          <- 唯一可执行文件
└── share/              <- 文档和 shell 补全脚本

devroot/venv/data-gh/   <- 隔离配置目录（通过 GH_CONFIG_DIR 指定）
├── config.yml          <- gh 配置文件（含 host、oauth_token）
└── hosts.yml           <- 多主机认证信息
```

### 2.2 隔离认证方案（Headless 自动化）

gh CLI 的认证方式中，**唯一适合自动化脚本**的是环境变量注入：

```powershell
# 方案 A：环境变量（推荐，零配置残留）
$env:GH_TOKEN = $env:GITHUB_PAT           # 从 .env 读取 PAT
$env:GH_CONFIG_DIR = "D:\pjt\cursor\cs_py\venv\data-gh"  # 隔离配置目录
& "D:\pjt\cursor\cs_py\venv\gh\bin\gh.exe" pr merge --merge --delete-branch

# 方案 B：配置文件（不推荐，需管理文件生命周期）
# echo $env:GITHUB_PAT | & "gh.exe" auth login --with-token --insecure-storage
```

**认证隔离性评估**：

| 方式 | 隔离性 | 持久化 | 适用场景 |
|------|--------|--------|---------|
| `GH_TOKEN` 环境变量 | 进程级隔离，无残留 | 仅当前进程 | **自动化脚本首选** |
| `GH_CONFIG_DIR` + 配置文件 | 目录级隔离 | 长期有效 | 交互式使用 |
| Windows Credential Store | 系统级共享 | 长期有效 | 桌面用户，不适合 Agent |

> **结论**：在 workflow 自动化场景下，**不需要 `gh auth login`**。直接通过 `GH_TOKEN` + `GH_CONFIG_DIR` 环境变量即可实现完全 headless 的隔离调用。


## 三、PR Merge 自动过程分析

### 3.1 完整闭环链条

```
本地开发 (devroot)
    |
    v
git add/commit (隔离 git)
    |
    v
git push (Step 7)
    |
    v
远程 GitHub 仓库
    |
    v
git pull (拉取最新)
    ^
    |
gh pr merge (Step 11)
    ^
    |
gh pr create (Step 10)
```

### 3.2 `gh pr merge` 命令能力矩阵

| 参数 | 作用 | 自动化场景适用性 |
|------|------|----------------|
| `--merge` | 创建 merge commit（保留所有 commit） | 默认策略 |
| `--squash` | 压缩为单个 commit 后 merge | 保持历史整洁 |
| `--rebase` | rebase 后 fast-forward merge | 可能冲突 |
| `--delete-branch` | merge 后删除本地和远程分支 | 自动清理 |
| `--auto` | 仅在满足检查要求后自动 merge | 需 CI/CD 配合 |
| `--admin` | 绕过保护规则强制 merge | 谨慎使用 |
| `--subject "<text>"` | 自定义 merge commit 标题 | 可注入 commit message |
| `-R <owner/repo>` | 指定仓库（非当前目录） | 显式指定更安全 |

### 3.3 关键认知偏差纠正

用户提到"在本地完成所有闭环"。这里需要明确：

> **PR merge 不是本地操作**。无论通过 gh CLI、GitHub Web 还是 GitHub API，代码合并都在**远程 GitHub 服务器**上执行。本地仓库在 merge 完成后需要执行 `git pull` 才能同步最新状态。

真正的"本地闭环"是：

```
本地 push -> 远程 PR 创建 -> 远程 PR merge -> 本地 git pull
     ^______________________________________________|
```

`gh pr merge` 只能完成中间两步的**命令行触发**，无法让合并过程发生在本地磁盘。


## 四、与现有 workflow 的集成方案

### 4.1 方案 A：扩展 workflow-deploy-full.py（新增 Step 10-11）

在现有 Step 9（Issue Sync）之后追加：

```python
# Step 10: PR Create（可选，若当前分支无 PR）
steps.append(("Step 10: pr create", _GH_EXE, [
    "pr", "create",
    "--title", step5_message,
    "--body", "Auto-generated by workflow-deploy-full",
    "--base", "main"
]))

# Step 11: PR Merge
steps.append(("Step 11: pr merge", _GH_EXE, [
    "pr", "merge",
    "--merge", "--delete-branch",
    "--subject", step5_message
]))
```

**问题**：
- PR create 需要分支策略配合（不能直接在 main 上开发）
- 如果仓库开启了"Require pull request reviews before merging"分支保护规则，`gh pr merge` 会失败（除非用 `--admin` 强制）
- 单人仓库通常不开启分支保护，此时 PR 流程是多余的（可以直接 push 到 main）

### 4.2 方案 B：独立 workflow（按需调用）

不修改现有 workflow，新增独立的 PR merge workflow：

```powershell
# 场景：用户明确说"merge 当前分支的 PR"
"${devroot}\venv\py\python.exe" "${devroot}\references\tasks\deploy-git-isolated\scripts\py-tools\workflow-pr-merge.py" `
    --devroot "${devroot}" `
    --strategy merge `
    --delete-branch
```

**优势**：不与现有部署流程耦合，按需触发。

### 4.3 方案 C：gh CLI 作为通用工具登记（不绑定 workflow）

仅将 gh CLI 纳入 `verified-runtime-index.json` 和 `verified-task-index.json`，作为**可用工具**登记，不修改任何 workflow。

```json
{
  "gh_cli": {
    "executable": "D:\\pjt\\cursor\\cs_py\\venv\\gh\\bin\\gh.exe",
    "version": "2.95.0",
    "role": "GitHub CLI（隔离配置，headless 调用）",
    "env_vars": ["GH_TOKEN", "GH_CONFIG_DIR"]
  }
}
```


## 五、风险评估

| 风险 | 等级 | 说明 |
|------|------|------|
| **分支保护冲突** | 高 | 若仓库开启"Require PR reviews"，自动化 merge 会失败 |
| **单人仓库价值低** | 中 | 无分支保护时，PR 流程是多余步骤 |
| **gh CLI 版本漂移** | 中 | 需定期更新 gh CLI 版本（可通过真源检测覆盖） |
| **认证 Token 泄露** | 高 | `GH_TOKEN` 在环境变量中传递，需确保不进入日志 |
| **合并冲突** | 中 | 若远程 main 有更新而本地未 pull，`gh pr merge` 会失败 |
| **网络依赖** | 低 | gh CLI 调用 GitHub API，国内需代理（与本项目代理体系衔接） |


## 六、执行建议（按优先级排序）

### 建议 1：先登记 gh CLI 为可用工具，暂不集成 workflow（推荐）

1. 下载 `gh_2.95.0_windows_amd64.zip` 到 `d:/download/`
2. 解压到 `devroot/venv/gh/`
3. 更新 `verified-runtime-index.json` 登记 gh CLI
4. **不修改任何 workflow**，仅作为工具可用

**理由**：先让 gh CLI 可用，用户可以在终端手动验证 `gh pr merge` 在自己仓库的实际行为（是否触发分支保护、是否需要 `--admin`），再决定是否自动化。

### 建议 2：若验证通过，新增独立 workflow（次推荐）

1. 创建 `workflow-pr-merge.py`（独立编排器）
2. 支持 `--strategy merge/squash/rebase`
3. 支持 `--delete-branch`
4. 支持 `--admin`（强制绕过保护，需用户显式授权）

**理由**：PR merge 与 deploy 是不同语义的操作（deploy 是"推送变更"，merge 是"合并审查"），解耦更符合职责分离。

### 建议 3：不扩展现有 deploy workflow（不推荐）

直接在 `workflow-deploy-full.py` 末尾追加 Step 10-11 会导致：
- 单用户仓库中 PR 流程无意义
- 分支保护冲突时整个 workflow 失败
- 破坏现有"push 即发布"的简洁语义

## 八、结论

> **gh CLI 隔离部署已完成，PR Merge 自动化在技术层面完全可行。** 是否推进到 workflow 集成阶段，取决于用户仓库是否启用了分支保护规则以及是否有多人协作的 Code Review 需求。

| 问题 | 答案 |
|------|------|
| gh CLI 能隔离部署吗？ | 能，`venv/gh/bin/gh.exe` + `GH_CONFIG_DIR` + `GH_TOKEN` |
| 能在本地完成 PR merge 吗？ | 能触发，但 merge 发生在远程服务器，本地需 `git pull` 同步 |
| 值得集成到 task/ 下吗？ | 视场景而定。单人仓库价值低；团队协作/分支保护场景有价值 |
| 建议的执行路径？ | 先手动验证 `gh pr merge` 行为 → 再决定是否自动化 |
