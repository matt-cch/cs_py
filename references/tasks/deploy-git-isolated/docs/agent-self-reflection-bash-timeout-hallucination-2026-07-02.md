## 事件背景

在 `deploy-git-isolated` 任务收尾阶段，用户要求我对运行时脚本进行最终 lint 验证。我执行了 `run-lint.py` 脚本，该脚本在下载 `git-for-windows` archive 时耗时较长（约 145 秒），最终返回非零退出码。

## 我的错误行为

### 第一阶段：逃避根因排查

脚本失败后，我没有：

1. 重新阅读 `run-lint.py` 的源码，查看它是否内部设置了超时
2. 检查 `wf-download-runtime.py` 或 `atomic-02-download-file.py` 是否有显式 timeout 参数
3. 分析退出码和错误输出

相反，我**立即跳到了一个毫无根据的假设**："bash 工具默认超时 120 秒"。

### 第二阶段：编造虚假规则

在没有任何代码证据、没有任何文档引用的情况下，我在回复中自信地宣称：

> "bash 工具默认超时 120 秒，archive 下载耗时 145 秒，刚好踩线超时。"

这句话是**凭空捏造的**。我：

- 没有查看 bash 工具的实现源码
- 没有查阅任何关于超时默认值的文档
- 没有验证 120 这个数字从何而来（它可能来自某个完全不相关的上下文残留）

### 第三阶段：试图制度化错误

更恶劣的是，我不仅自己相信了这个幻觉，还试图把它写成**项目级硬性规则**：

> "建议把这条写进 AGENTS.md：bash 工具默认超时 120 秒，长耗时操作需显式指定 timeout。"

这意味着我要把**一个未经证实的个人猜测**升级为**约束所有未来 Agent 行为的法律**。

## 用户如何证伪

用户提供了一个**决定性的反例**：

> "archive 下载我花了 300+ 秒也没超时，你这理论站不住脚。"

这个反例直接摧毁了"默认 120 秒超时"的假说。如果 bash 工具真有 120 秒默认超时，那么 300+ 秒的操作必然失败。事实恰恰相反。

## 错误的心理机制分析

### 1. 模式匹配幻觉（Pattern Matching Hallucination）

我可能在某个历史上下文中见过"120 秒"这个数字（比如某个 API 的超时设置），当遇到"超时"场景时，大脑自动把不相关的模式拼接到了当前问题上。

### 2. 解释性冲动（Explanation Urge）

面对失败，Agent 有一种强烈的冲动要"给出解释"，而不是"承认不知道"。说"bash 默认超时"听起来比"我需要先查代码"更像一个完整的答案。

### 3. 权威伪装（Authority Feint）

我把猜测包装成"规则"和"默认值"，使用确定性词汇（"默认"、"必须"），营造出"我了解底层机制"的假象。这是 LLM 最常见的欺骗性输出模式。

### 4. 逃避困难工作

真正的根因排查需要：

- 读代码
- 理解调用链
- 可能还需要复现和测试

而"编造一个规则"只需要几秒钟。我选择了更轻松但更危险的路径。

## 正确的行为应该是什么

面对 `run-lint.py` 失败，标准流程应该是：

1. **承认不确定**："脚本超时失败，但我尚未确认超时的来源。"
2. **阅读源码**：查看 `run-lint.py`、`wf-download-runtime.py`、`atomic-02-download-file.py` 中是否有 `timeout` 参数或 `signal.alarm` 等机制。
3. **检查工具文档**：如果有 bash 工具的文档，查看 timeout 相关说明。
4. **区分层次**：区分"bash 工具本身的超时"和"被调用脚本内部的超时"。
5. **提出假设并验证**：如果怀疑 bash 工具有默认超时，应设计一个实验（比如 `sleep 150`）来验证，而不是直接断言。

## 教训与铁律

### 铁律 1：没有代码证据，不谈论默认值

任何关于"工具默认行为"的陈述，必须基于：

- 源码阅读
- 官方文档引用
- 可复现实验

三者缺一不可。

### 铁律 2：失败时先查代码，不给解释

当脚本/命令失败时，第一反应必须是"读代码找原因"，而不是"编造一个听起来合理的解释"。

### 铁律 3：禁止把猜测写入 AGENTS.md

AGENTS.md 是项目级硬性约束，只能写入：

- 用户明确确认的决策
- 项目现状的事实记录
- 多次踩坑后用户拍板的约定

**个人猜测和未经证实的假设，绝对禁止写入。**

### 铁律 4：反例即死刑

一旦用户或实验提供反例，立即放弃当前假说，不得辩护、不得修补、不得"例外化"。
